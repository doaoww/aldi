# Aldi — технический план MVP

## 1. Цель

Создать веб-приложение для женщин после родов с тремя связанными возможностями: разговор с голосовой или текстовой помощницей, подготовка карточки для врача и отдельный раздел с 3D-инструкциями упражнений. Врач получает доступ к карточкам, которые пациентки самостоятельно отправили ему.

План основан на исходном плане Sana (Lovable + Next.js/Railway + ElevenLabs), адаптированном под Aldi. Это план разработки, а не описание уже реализованных функций. Распределение времени и стек — предложения для команды; правила мероприятия и доступность сервисов нужно проверить отдельно.

## 2. Объём MVP и демо

**Основной сценарий:** пациентка открывает Aldi → выбирает голос или текст → описывает самочувствие → проверяет и при желании исправляет карточку → отдельно подтверждает отправку врачу → врач видит карточку в дашборде. После разговора пациентка видит плашку со ссылкой на упражнения.

**Упражнения входят в MVP:** отдельный пункт меню доступен без разговора; в нём есть каталог нескольких упражнений и экран хотя бы с одной работающей 3D-анимацией, демонстрирующей движение и дыхание, с паузой и повтором. Остальные карточки показывают только действительно готовые материалы; отсутствие модели обозначается явно. Для демонстрации допустимы заранее подготовленные модели и анимации: генерация 3D искусственным интеллектом не требуется.

Контент упражнений, дыхательные инструкции и условия применения подготавливаются и проверяются профильным специалистом. До проверки их можно показывать только как демонстрационные материалы на вымышленных примерах, не предлагая как медицинскую рекомендацию.

## 3. Путь пользователя и экраны

### Пациентка

1. **Главная:** краткое объяснение, кнопка «Поговорить с Aldi», пункты «Моя карточка» и «Упражнения».
2. **Начало разговора:** информация об обработке данных и отдельных внешних сервисах; явное согласие на обработку для разговора. Кнопки «Говорить» и «Написать».
3. **Разговор:** голосовой сеанс или текстовый режим; пациентка может завершить беседу. Живое превью карточки — опционально, если оно не задерживает основной сценарий.
4. **Моя карточка:** сведения с цитатами, отсутствующие данные помечены «Не указано», возможность исправить текст и подготовить вопросы врачу. Исправленный женщиной текст обозначается как изменённый; его нельзя выдавать за проверенную дословную цитату.
5. **Отправка:** отдельное подтверждение с указанием получателя. До него карточка отсутствует в списке врача. Кнопка «Оставить себе» сохраняет её без отправки.
6. **Плашка после разговора:** «Посмотрите упражнения для восстановления» → «Открыть упражнения». Это переход к общему каталогу, а не персональное назначение по словам ИИ.
7. **Упражнения:** каталог карточек → экран выбранной 3D-анимации с пояснениями, воспроизведением, паузой и повтором. Раздел доступен и с главной.

### Врач

1. Вход в защищённый дашборд.
2. Список только отправленных карточек: дата, краткое описание, статус и отметка срочности при наличии.
3. Карточка с данными, исходными цитатами и пометками об изменениях пациентки; действие «Просмотрено».

Назначение упражнений через дашборд — следующий этап. В MVP врач может обсуждать упражнения на консультации; не показываем в интерфейсе неработающую функцию как готовую.

## 4. Архитектура

```text
Браузер пациентки / врача — Lovable, React
  ├─ голосовой сеанс ↔ ElevenLabs (напрямую)
  ├─ 3D-плеер ← подготовленные GLB/glTF + анимация
  └─ HTTPS API ↔ Next.js на Railway
                    ├─ PostgreSQL / Prisma: карточки, согласия, упражнения
                    ├─ LLM через OpenRouter: структурирование рассказа
                    ├─ ElevenLabs: выдача данных для голосового сеанса
                    └─ опционально: уведомление врачу без медицинского текста
```

- **Фронтенд:** React / TypeScript в Lovable; адаптация для телефона и доступное управление с клавиатуры.
- **API:** Next.js App Router / TypeScript, проверка входных данных через Zod.
- **Хранение:** PostgreSQL и Prisma. На демо — только вымышленные данные.
- **Голос:** ElevenLabs; возможность продолжить текстом при отказе микрофона или сервиса.
- **3D:** React Three Fiber / Three.js и заранее подготовленные модели GLB/glTF. Начать с одной проверенной модели и одной анимации, затем добавлять упражнения по готовности. Уточнить наличие прав на использование моделей и музыки/озвучки.
- **Размещение:** фронт Lovable, API и база Railway, как в исходном плане; до разработки проверить условия организаторов и доступность интеграций. Если внешний бэкенд запрещён, перенести API в разрешённую среду, сохранив те же сценарии.

## 5. 3D-плеер и контент

Каждое упражнение содержит `id`, название, описание, путь к модели, имя анимации, инструкцию по дыханию, длительность, статус проверки специалистом и при необходимости текст противопоказаний. Точные упражнения и инструкции выбираются вместе со специалистом, а не генерируются моделью на лету.

Плеер загружает модель и анимацию, показывает прогресс, кнопки «Воспроизвести / Пауза» и «Повторить», а также текстовую инструкцию, доступную без звука. Для дыхания можно использовать синхронизированную текстовую подсказку; её содержание и тайминги проверяются специалистом. На мобильном устройстве ограничить размер файлов и качество рендера; при ошибке WebGL или загрузки показать понятную текстовую инструкцию и сообщение, что 3D недоступно.

Подготовка одного упражнения: согласовать сценарий со специалистом → получить модель и права на неё → подготовить анимацию и дыхательные подсказки → проверить синхронизацию и понятность → протестировать на телефоне → опубликовать проверенную версию. При отсутствии специалиста или готового ассета использовать демонстрационный, явно обозначенный пример; не изображать его проверенным.

## 6. Данные и состояния

Предлагаемые сущности:

- **Intake:** идентификатор, владелец сессии, время, статус, транскрипт, признаки срочности и версия согласия.
- **Card:** поля жалоб, цитаты, признак проверки цитаты, отметка об исправлении пациенткой, вопросы врачу.
- **Share:** карточка, выбранный врач/клиника, время и факт отдельного согласия на отправку, состояние отправки.
- **Exercise:** метаданные, ссылка на 3D-файл, анимация, инструкции и статус клинической проверки.
- **Doctor:** учётная запись, роль и принадлежность к клинике.

Статусы разговора: `IN_PROGRESS → READY → SHARED → REVIEWED`. Срочность — отдельный признак, а не замена статуса: отправленная срочная карточка остаётся отправленной. Завершение разговора само по себе не отправляет данные врачу.

Цитата проверяется по репликам пациентки, а не помощницы. При отсутствии подтверждения показывается «Проверьте»; при отсутствии данных — «Не указано». Проверка совпадения текста не гарантирует медицинскую достоверность и не должна подаваться как полная защита от ошибок ИИ.

## 7. API: предлагаемые контракты

| Метод | Маршрут | Назначение и доступ |
|---|---|---|
| POST | `/api/intakes` | Создать разговор после согласия; выдать защищённую пациентскую сессию. |
| GET | `/api/intakes/:id` | Получить свою карточку; проверять сессию и права владельца. |
| POST | `/api/intakes/:id/complete` | Завершить разговор и сформировать черновик карточки; без отправки врачу. |
| PATCH | `/api/intakes/:id/card` | Исправить свою карточку; сохранять происхождение изменений. |
| POST | `/api/intakes/:id/share` | Явно отправить карточку выбранному врачу или клинике. |
| DELETE | `/api/intakes/:id` | Удалить доступные данные пациентки с понятным описанием исключений и сроков. |
| POST | `/api/voice/session` | Создать авторизованный голосовой сеанс; секреты остаются на сервере. |
| POST | `/api/tools/update-intake` | Опциональное живое превью; только проверенный вызов инструмента сервиса. |
| POST | `/api/tools/flag-urgent` | Зафиксировать признак срочности; только проверенный вызов инструмента. |
| GET | `/api/exercises` | Получить опубликованный каталог упражнений. |
| GET | `/api/exercises/:id` | Получить данные упражнения и ссылки на разрешённые материалы. |
| GET | `/api/doctor/intakes` | Список отправленных карточек в пределах прав врача. |
| GET | `/api/doctor/intakes/:id` | Просмотр отправленной карточки с проверкой принадлежности. |
| PATCH | `/api/doctor/intakes/:id` | Отметить карточку просмотренной. |

Все запросы валидируются; UUID сам по себе не является авторизацией. Секреты внешних сервисов не попадают во фронтенд. Если используется уведомление в Telegram, оно не содержит медицинских данных; ссылка ведёт в авторизованный кабинет. Отказ уведомления не отменяет уже сохранённую отправку.

## 8. Безопасность и медицинские границы

- Согласие на обработку для разговора и согласие на отправку врачу — отдельные действия. До отправки врач не видит карточку.
- Для пациентки нужна защищённая сессия; для врача — вход и проверка доступа к своей клинике. Демонстрация с общим паролем и вымышленными данными не равна готовности к работе с пациентами.
- Использовать HTTPS, ограничивать доступ и сроки хранения, не записывать транскрипты и токены в обычные логи. Описать, кто хранит данные и что происходит при удалении, включая внешних поставщиков.
- Помощница не диагностирует депрессию или другие заболевания, не назначает лекарства и не утверждает, что упражнение подходит конкретной женщине. Она может предложить обратиться к специалисту.
- При сообщениях об опасных симптомах или риске причинения вреда себе/ребёнку интерфейс должен немедленно показать заранее согласованную со специалистами инструкцию для экстренной помощи с учётом страны. Не обещать, что система обнаружит все опасные ситуации или что врач постоянно отслеживает сообщения. Проверка ключевых слов может быть дополнительным сигналом, но не заменяет клинически проверенный протокол.
- До работы с реальными пациентками необходимы клиническая проверка текстов, упражнений и кризисного сценария, а также проверка защиты данных и применимых требований с профильными специалистами.

## 9. Порядок реализации

1. Уточнить ограничения мероприятия, доступы к сервисам и наличие специалиста и разрешённых 3D-ассетов. Зафиксировать, что реально можно показать.
2. Поднять API и базу, проверить соединение фронта с `/api/health`; настроить защищённые сессии и демоданные.
3. Реализовать текстовый разговор → формирование карточки → редактирование → отдельное подтверждение отправки → список врача. Проверить весь путь на вымышленных данных.
4. Подключить ElevenLabs и сохранить текстовый режим как запасной сценарий. Проверить отказ микрофона и недоступность сервиса.
5. Создать раздел упражнений, подключить одну готовую 3D-анимацию, управление и текстовый fallback. Добавить другие готовые модели и плашку после разговора.
6. Добавить обработку срочных сообщений, проверить границы доступа, согласия и удаление. При наличии времени — живую карточку и уведомления врачу.
7. Провести сквозную проверку с телефона и подготовить резервное видео демонстрации.

Если времени мало, сокращать число готовых упражнений и необязательные эффекты, живое превью и уведомления, сохраняя отдельный раздел и хотя бы одну работающую 3D-демонстрацию. Если ассет или проверка специалиста не готовы, честно обозначить ограничение; не выдавать макет за работающую или клинически проверенную функцию.

## 10. Проверка перед демонстрацией

- Текстовый и, если подключён, голосовой сценарий формируют карточку без выдуманных подтверждённых цитат; её можно исправить.
- До явной отправки врач не видит карточку; после отправки её видит только назначенный получатель.
- Раздел упражнений открывается с главной и с плашки после разговора; 3D-анимация запускается, ставится на паузу и повторяется на телефоне; при ошибке показывается текст.
- Срочное сообщение вызывает согласованное сообщение пользователю; демонстрация не создаёт впечатления гарантированного обнаружения или круглосуточного наблюдения врача.
- Демоданные вымышлены и помечены; секреты и медицинские сведения не отображаются в логах и уведомлениях.

## 11. Демонстрация

Показать главную → короткий разговор на вымышленном примере → карточку и явную отправку → карточку в дашборде врача → плашку упражнений → 3D-анимацию с дыхательными подсказками. В финале объяснить, какие элементы проверены специалистом, а какие пока являются прототипом.

## 12. Результат пересмотра и обязательные уточнения (15 ноября 2026)

Текущий план соответствует идее Aldi, но предыдущая редакция была скорее архитектурным описанием: не хватало текстового диалога в API, обработки повторных запросов, конкретного механизма доступа, языковых контрактов и плана интеграции. Исходный план подробнее описывал разработку, однако автоматическая отправка после разговора и доступ по одному UUID не подходят согласованному сценарию Aldi. Ниже — обязательные дополнения; при расхождениях они уточняют разделы выше.

### 12.1 Четыре языка — требование MVP

Поддерживаем **русский (`ru`), казахский (`kk`), узбекский (`uz`), английский (`en`)**. Узбекский интерфейс MVP — латиница; ввод кириллицей не блокировать. Переключатель «Русский / Қазақша / O‘zbekcha / English» доступен на главной и в настройках врача. Выбор сохраняется на устройстве; язык браузера используется только как начальное предложение.

Переводятся навигация, согласия, ошибки, разговор, карточка, дашборд, каталог, инструкции и подсказки дыхания. Общие 3D-файлы используются для всех языков; тексты и аудиодорожки отделены от модели. Изменение языка интерфейса не переводит и не переписывает исходный транскрипт.

Фронтенд хранит словари `shared/i18n/locales/{ru,kk,uz,en}.json`, использует стабильные ключи и проверяет совпадение ключей в CI. Медицинские тексты и согласия проходят языковую проверку; автоматический перевод служит черновиком. Для отсутствующих инструкций не подставлять незаметно другой язык: явно обозначить недоступность и предложить выбор.

Для голоса настроить и проверить распознавание, ответы и произношение на каждом из четырёх языков. Поддержка языков зависит от выбранной конфигурации ElevenLabs; список языков синтеза сам по себе не доказывает качество всего разговора. Официальная документация включает эти языки, но выбранный агент должен пройти отдельный сквозной тест. До успешного теста показывать фактическую доступность голоса и предлагать текст на выбранном языке; такой режим не считать выполненной четырёхъязычной голосовой поддержкой.

Источники: [языки ElevenLabs](https://elevenlabs.io/docs/help-center/other/what-languages-do-you-support), [языки ElevenAgents](https://elevenlabs.io/docs/help-center/product/eleven-agents/which-languages-can-i-use-with-eleven-agents), [настройка языка](https://elevenlabs.io/docs/eleven-agents/customization/voice/customization/language). Проверено 15 ноября 2026; конкретные версии SDK зафиксировать после интеграционного теста.

### 12.2 Язык в данных и API

- `Intake.locale`: выбранный язык разговора; `Message.language`: язык конкретной реплики при необходимости, включая смешанную речь.
- `Card.sourceLocale`: язык исходных данных; `CardTranslation`: язык перевода, версия исходной карточки, переведённые значения, пометка машинного перевода.
- Оригинальные цитаты всегда остаются на исходном языке. Перевод показывается рядом с маркировкой «Перевод» и никогда не получает признак проверенной дословной цитаты. После исправления карточки переводы инвалидируются.
- `ExerciseTranslation`: `exerciseId`, `locale`, название, пояснения, инструкции, подсказки, ссылка на озвучку и статус проверки. Публикация контролируется отдельно для каждого языка.
- `POST /api/intakes`: `{ locale, consentVersion, consent: true }`; страна задаётся отдельно от языка. Язык не определяет страну или экстренные контакты.
- `POST /api/intakes/:id/messages`: `{ message, clientMessageId }` → сохраняет реплику и возвращает ответ помощницы на выбранном языке. Это полноценный текстовый диалог, а не только отправка одного текста на извлечение.
- `POST /api/voice/session`: `{ intakeId }`; сервер выбирает конфигурацию по сохранённому языку и привязывает сеанс к владельцу.
- `GET /api/exercises?locale=kk` и `GET /api/exercises/:id?locale=kk`: локализованные материалы с явным статусом доступности.
- `POST /api/intakes/:id/translations`: `{ targetLocale }`; доступ владельцу или уполномоченному врачу, оригинал сохраняется.
- Неподдерживаемый язык → 400 с локализованным сообщением; коды ошибок стабильны и не зависят от языка.

### 12.3 Надёжность и права доступа

Предлагаемое решение для разных доменов Lovable и Railway: пациентке выдаётся случайный короткоживущий bearer-токен, в базе хранится его хеш. Токен передаётся только в заголовке, хранится в памяти или sessionStorage, не включается в URL; срок истечения явно объясняется. Это анонимная сессия без восстановления на другом устройстве в MVP. Врач входит через готовый провайдер аутентификации; API проверяет токен и принадлежность клинике. CORS — точный список разрешённых origin, лимиты на создание сеансов и запросы LLM. Для пилота предпочтительно единое происхождение с HttpOnly-сессиями.

`complete` сначала сохраняет доступный транскрипт, затем запускает извлечение. Обрыв связи не считается успешным завершением: UI предлагает продолжить или явно завершить. Сервер проверяет привязку внешнего conversation ID к intake; клиентский текст не выдаётся за подтверждённый провайдером транскрипт. Повторный `complete` возвращает существующий результат для той же версии; ошибка LLM оставляет сохранённый разговор и возможность повтора. Состояние обработки `IDLE / PROCESSING / FAILED / DONE` хранится отдельно от бизнес-статуса.

`share` отправляет конкретную неизменяемую версию карточки. Правка после отправки создаёт новый черновик; повторная отправка требует подтверждения. Ключ идемпотентности и уникальность отправки исключают дубли. Уведомление создаётся после записи отправки, повторяется отдельно и не приводит к повторной отправке карточки. Срочный флаг до согласия показывается пациентке, но не раскрывает разговор врачу.

Проверенные инструменты агента привязываются сервером к сеансу: одного переданного моделью `intake_id` недостаточно. Проверять секрет/подпись, повторные вызовы и допустимые поля. Позднее обновление превью не должно перезаписывать финальную карточку.

До функций развернуть `/api/health`, проверить доступ с опубликованного фронта, миграции и статические 3D-файлы. Зафиксировать версии зависимостей lock-файлом; команды сборки и миграций проверить на выбранных версиях. После этого интегрировать текстовый вертикальный сценарий, затем голос и 3D. Не переносить старые часы мероприятия автоматически.

### 12.5 Распределение работы и контроль объёма

Для команды из четырёх человек: A — интерфейс и локализация; B — API, база, доступ и отправка; C — голос, извлечение и четыре языка; D — подготовка/интеграция 3D, проверка контента и демо. Финальный QA — совместно. Это предложение распределения, а не утверждение о составе команды.

Трёхчасовой срок из исходника с добавленными 3D и четырьмя языками нельзя обещать без заранее готовых ассетов, переводов и доступов. Контрольные точки: (1) опубликованный API и тест языков; (2) текст → карточка → отдельная отправка → врач; (3) рабочая 3D-анимация и каталог; (4) голос и все четыре языка; (5) сквозная проверка. Если времени недостаточно, сначала убирать Telegram, живое превью, печать и визуальные эффекты. Не скрывать отсутствие языка или 3D за неработающей кнопкой.

### 12.6 Дополнительные критерии приёмки

На **каждом из ru, kk, uz, en** проверить: выбор языка, согласия, текстовую беседу, голосовую беседу, итоговую карточку, оригинал и перевод, дашборд, инструкции упражнений, ошибки и срочное сообщение. Проверить смешанную речь, казахские буквы и узбекские апострофы: нормализация не должна превращать разные слова в ложное совпадение цитат.

Автоматические проверки: одинаковые ключи словарей; отсутствие доступа по чужому intake ID; отсутствие карточки у врача до share; повторные complete/share без дублей; сохранность данных при отказе LLM/уведомления; цитата помощницы не принимается как цитата пациентки; перевод не маркируется оригиналом. Вручную: телефон, медленная сеть, запрет микрофона, пауза/повтор 3D и синхронизация дыхательных подсказок после паузы. При срочном сигнале плашка упражнений не предлагается как решение проблемы.

## 13. Авторизация и управление пациентами — актуальная модель

Этот раздел заменяет анонимную сессию из раздела 12.3 и уточняет маршруты выше. И пациентка, и врач входят по логину и паролю. При первом входе каждый получает роль и видит соответствующий интерфейс. Врач работает только с пациентками своей клиники и в пределах предоставленных ему прав.

### Сценарий

1. Администратор создаёт аккаунт врача и назначает его клинике. Самостоятельная регистрация врача в MVP не предполагается.
2. Врач входит в дашборд, открывает «Пациентки» → «Добавить пациентку», вводит необходимые данные и выбирает язык интерфейса. Система создаёт профиль со статусом `INVITED` и одноразовое приглашение с ограниченным сроком действия.
3. Приглашение передаётся через заранее согласованный безопасный канал. Пациентка открывает его, задаёт собственный логин и пароль и входит в Aldi. Не отправлять пароль открытым текстом; способ доставки приглашения на демо показывается без реальных контактных данных.
4. Врач может просматривать список своих пациенток и профиль с минимальными данными, обновлять контактную информацию и повторно создавать приглашение. Разговоры и карточки доступны врачу только после отдельной отправки пациенткой. Факт создания профиля не является согласием на передачу содержания разговоров.
5. Пациентка входит, выбирает язык, принимает согласие на обработку данных и пользуется разговором и упражнениями. При отправке карточки она видит имя врача или клиники и отдельно подтверждает отправку.
6. Потеря пароля: одноразовая ссылка с ограниченным сроком, доставленная через подтверждённый канал. Если канал не настроен, для демо — ручное повторное приглашение с инвалидированием старого; для реальных пользователей восстановление должно быть реализовано до запуска.

### Сессии и защита

Предпочтителен проверенный поставщик аутентификации с серверными сессиями: HTTPS, безопасный HttpOnly cookie, `Secure`, `SameSite` и защита от CSRF. При разных доменах фронта и API предусмотреть корректную cookie/CORS-конфигурацию или использовать единый домен через прокси. Пароли хранит провайдер в виде стойких хешей; лимитировать попытки входа, поддерживать выход и отзыв сессий. Врачебные операции и каждый доступ к пациенту проверяются на сервере по роли, клинике и связи врача с пациенткой. Логи доступа не содержат паролей, токенов и медицинских текстов. Для реального запуска предусмотреть MFA для врачей и аудит доступа.

### Модель данных

- `User`: `id`, уникальный `login`, `role` (`PATIENT | DOCTOR | ADMIN`), `locale`, `status`, `createdAt`; пароль и сессии управляются провайдером.
- `Clinic`: `id`, `name`.
- `DoctorProfile`: `userId`, `clinicId`, `displayName`.
- `PatientProfile`: `id`, `userId?`, `clinicId`, `displayName`, `status` (`INVITED | ACTIVE | ARCHIVED`); контактные данные — только необходимые для приглашения.
- `DoctorPatient`: `doctorId`, `patientId`, статус связи; уникальность пары и проверка принадлежности клинике.
- `Invitation`: хеш одноразового токена, пациентка, срок, статус; токен не хранится открытым текстом.
- `Intake.patientId` указывает на профиль пациентки; `Share` связывает конкретную версию карточки с выбранным врачом. Архивирование профиля не означает автоматическое удаление медицинских записей: политика хранения и удаления определяется отдельно.

## 14. Контракты API

Все маршруты используют JSON и HTTPS. Успешные ответы имеют форму `{ "data": ... }`, ошибки — `{ "error": { "code": "...", "message": "..." } }`; сообщения локализованы, коды стабильны. `400` — неверный ввод, `401` — нет сессии, `403` — нет права, `404` — объект недоступен, `409` — конфликт версии, `429` — лимит, `500/503` — ошибка сервиса. Идентификаторы непрозрачны и сами по себе не дают доступа. Клиент передаёт `Idempotency-Key` при создании разговора, завершении и отправке.

| Метод и путь | Вход | Результат / права |
|---|---|---|
| `POST /api/auth/login` | `{ login, password }` | Сессия и `{ user: { id, role, locale } }`; одинаковое сообщение при неверном логине и пароле. |
| `POST /api/auth/logout` | — | Отзыв текущей сессии. |
| `GET /api/auth/me` | — | Текущий пользователь и роль. |
| `POST /api/auth/invitations/accept` | `{ token, login, password }` | Активация один раз до истечения срока. |
| `POST /api/auth/password-reset` | `{ login }` | Одинаковый ответ независимо от существования аккаунта. |
| `GET /api/doctor/patients` | фильтр и пагинация | Пациентки, доступные текущему врачу. |
| `POST /api/doctor/patients` | `{ displayName, locale, contact }` | Создание профиля и приглашения; только врач своей клиники. |
| `GET /api/doctor/patients/:id` | — | Профиль и список отправленных врачу карточек. |
| `PATCH /api/doctor/patients/:id` | `{ displayName?, contact?, locale? }` | Изменение разрешённых полей. |
| `POST /api/doctor/patients/:id/invitations` | — | Новое приглашение; старое отзывается. |
| `POST /api/intakes` | `{ locale, consentVersion, consent: true }` | `{ id, status: "IN_PROGRESS" }`; пациентка из сессии. |
| `POST /api/intakes/:id/messages` | `{ message, clientMessageId }` | `{ message, assistantMessage }`; только владелица. |
| `POST /api/voice/session` | `{ intakeId }` | Данные сеанса, привязанного к пациентке и разговору. |
| `POST /api/intakes/:id/complete` | `{ expectedVersion }` | Сохранение разговора и `{ processingStatus, card? }`; без отправки. |

Вызовы `tools/update-intake` и `tools/flag-urgent` доступны только внешнему провайдеру после проверки подписи или секрета и привязки сеанса. Запросы пациента не принимают `patientId` или роль как основание для доступа: они определяются сервером.

### Контракты домена и портов

```ts
type Locale = 'ru' | 'kk' | 'uz' | 'en';
type Role = 'PATIENT' | 'DOCTOR' | 'ADMIN';
type Message = { id: string; role: 'patient' | 'assistant'; text: string; language: Locale };
type CardField = { value: string | null; quote: string | null; quoteVerified: boolean; editedByPatient: boolean };
type Card = { version: number; sourceLocale: Locale; fields: Record<string, CardField>; doctorQuestions: string[] };
type Exercise = { id: string; locale: Locale; title: string; modelUrl: string; animationName: string; instructions: string[]; reviewed: boolean };
interface IntakeRepository { getForPatient(id: string, patientId: string): Promise<Intake | null>; save(intake: Intake, expectedVersion: number): Promise<void>; }
interface CardExtractor { extract(messages: Message[], locale: Locale): Promise<Card>; }
interface VoiceProvider { createSession(intakeId: string, locale: Locale): Promise<{ sessionUrl: string }>; }
interface NotificationPort { notifyNewShare(shareId: string): Promise<void>; }
// Intake — доменная сущность с id, patientId, status, messages и version.
```

Это целевые контракты, а не существующий код. Адаптер голосового сервиса может возвращать иной тип сессии; он должен быть приведён к единому внутреннему контракту. Неизвестные поля карточки запрещаются схемой валидации; проверки цитат выполняются по репликам пациентки на языке оригинала.

## 15. SOLID и Feature-Sliced Design

Бэкенд: **S** — отдельные обязанности маршрутов, сценариев, доменных правил и адаптеров; **O** — добавление поставщика голоса или модели через реализацию порта; **L** — адаптеры соблюдают одинаковые контракты ошибок и результата; **I** — небольшие интерфейсы для разговора, хранения, уведомлений; **D** — сценарии зависят от доменных портов, конкретные адаптеры подключаются в composition root. Не вводить абстракции там, где нет реальной границы или необходимости тестирования.

Фронтенд использует **Feature-Sliced Design (FSD)**: `app` (провайдеры и роуты), `pages` (экраны), `widgets` (крупные блоки), `features` (действия: вход, добавление пациентки, отправка карточки, выбор языка), `entities` (пользователь, пациентка, карточка, упражнение), `shared` (API, UI, локализация). Импорт — из нижележащих слоёв через публичный API слайса; страницы не обходят серверные проверки прав. Для небольшого MVP достаточно указанных слоёв без искусственного дробления.

## 16. Дополнительная приёмка

- Врач добавляет пациентку; приглашение одноразовое и истекает; пациентка создаёт пароль и входит. Неверный пароль и исчерпание лимита обрабатываются корректно.
- Другой врач или клиника не получает доступ к профилю или карточке без прав; пациентка не видит чужие записи. Подмена ID и роли в запросах не помогает.
- Врач видит профиль после добавления, но не видит черновики разговоров; карточка появляется только после отдельной отправки. Повторный вход и выход не ломают доступ.
- Проверить восстановление доступа, отзыв приглашения, CSRF, истечение сессии и обработку повторных запросов. Демоданные и приглашения — только вымышленные.
- Обновить порядок работ: сначала вход и создание пациентки, затем текстовый сценарий и отправка, врачебный кабинет, голос, четыре языка и 3D; локализацию и проверки безопасности проектировать с самого начала.

Типы и языки `ru | kk | uz | en` должны совпадать у всех. Фронтенд может начинать на моках тех же контрактов. Документ контрактов нужно создать при подготовке репозитория; сейчас это требование к проекту, а не утверждение о наличии файла.

Промпт участникам для их ИИ-инструментов:

> Прочитай docs/IDEA.md, docs/TECH_PLAN.md и docs/API_CONTRACTS.md. Работай в своей согласованной зоне. Не меняй общие контракты, схему базы, роутер и зависимости без согласования; необходимые изменения вне зоны перечисли отдельно.

### Объединение работы

Каждый участник регулярно делает небольшие коммиты и отправляет свою ветку, предварительно проверяя изменения и отсутствие секретов:

```bash
git status
git add .
git commit -m "Add patient login screen"
git push -u origin feat/frontend
```

Имя ветки и сообщение заменяются на свои. `.env`, токены и пароли не коммитятся; настроить `.gitignore` и хранить пример переменных в `.env.example` без секретов. Участник открывает pull request в `main`, координатор проверяет и объединяет. Остальные регулярно обновляют свои ветки:

```bash
git fetch origin
git merge origin/main
```

Объединять постепенно: (1) каркас и контракты; (2) вход и пациентки; (3) текст → карточка → отправка → дашборд; (4) голос; (5) упражнения и 3D; (6) проверка четырёх языков. После каждого объединения запускать сборку и проверять затронутый сценарий. Не откладывать первую интеграцию до финального часа.

### Размещение

Предлагаемый вариант: Vercel для фронтенда, Railway для API и PostgreSQL. Это вариант вместо размещения фронтенда на Lovable, упомянутого ранее; Lovable при желании остаётся инструментом создания интерфейса. Перед выбором проверить ограничения мероприятия. Подключить оба сервиса к одному репозиторию:

| Сервис | Корневая папка | Настройка |
|---|---|---|
| Vercel | `frontend` | Команда сборки и выходная папка соответствуют выбранному проекту; для Vite обычно `npm run build` и `dist`. Настроить fallback клиентских маршрутов. |
| Railway API | `backend` | Сборка Next.js, миграции перед запуском и запуск на предоставленном порту. |
| Railway PostgreSQL | отдельный сервис | `DATABASE_URL` доступен только бэкенду. |

Секреты ElevenLabs, OpenRouter и авторизации задаются в окружении бэкенда; фронтенду передаются только публичные настройки. Для cookie-сессии предпочтителен прокси `/api/*` через домен фронтенда к Railway; проверить cookie, CSRF, CORS, вход и выход на опубликованном сайте. Точные команды сборки и миграций зависят от фактически созданного проекта и проверяются до демонстрации.

Первый деплой выполнить сразу после каркаса: опубликованная главная и работающий `/api/health`. Затем подключать остальные функции и проверять их на опубликованных URL. На демо использовать вымышленные данные.

Документация: https://vercel.com/docs/monorepos и https://docs.railway.com/deployments/monorepo.
